# ODYS PARFUM — website

Static, zero-install. No framework, no build step, no dependencies.

## Run

```bash
python -m http.server 4173
```

Then open <http://localhost:4173>. (Opening `index.html` from disk works too.)

## The business model, as coded

| | Price | Points |
|---|---|---|
| **LE TRIO** — 3 parfums 50 ML, chosen by the customer | **199 MAD**, delivery included | ~2.9 |
| Parfum 50 ML | **69 MAD** | **1 point** |
| Diffuseur 50 ML + 3 sticks | **49 MAD** | **none** — outside the programme by design |
| Oud — bâtonnets, sold by the gram | per gram, falling with weight | by what you pay |

**Points follow the dirham: 1 point per 69 MAD of paid product** (`config.points.madPerPoint`), diffuseurs excluded. A parfum is exactly one point. Accrual is fractional per line and rounded once, at checkout.

> This replaced per-unit accrual. Keyed per gram, 20 points cost ~800 MAD of a 10 MAD/g batch but ~1,760 MAD of a 22 MAD/g one — the same reward for a third of the spend. Money-based accrual closes that.

Oud weights: **5 · 10 · 15 · 30 · 100 g**, minimum 5 g. Above 100 g it becomes a **special order** — the customer names the weight, the special rate applies, and the team confirms before shipping.

**Redemption ladder** — the first rung is reachable on a first order:

- **3 points** (~207 MAD) → a 2 ML discovery vial added to the next order
- **8 points** (~552 MAD) → a free diffuseur
- **20 points** (~1,380 MAD) → one free 50 ML perfume
- **50 points** → three free perfumes
- **100 points** → a custom coffret, composed by the customer, gift-wrapped and sendable to someone else

Redeeming converts points into a *voucher* held on the account; the voucher comes off automatically in the cart once an eligible item is in the bag, and a redeemed reward always ships free.

## Ordering — WhatsApp + cash on delivery

There is no payment gateway and no backend, by design for launch. `OD.waLink()` serialises the basket (items, weights, coffret composition, rewards applied, totals, name/address/city) into a `wa.me` message in the customer's language. Two entry points:

- **Order on WhatsApp** — the primary button in the cart, and a WhatsApp icon in the header plus the number in the footer (the trust signal a COD shopper looks for).
- **Or leave your address here** — the same form as before; submitting opens WhatsApp pre-filled *and* records the order locally so points and rewards still work.

⚠ `config.whatsapp` is a placeholder (`212600000000`). Put the real number there — or in `admin.html` — before showing anyone the site.

## Coffrets

`coffrets.html` is a five-step builder that asks **who it is for first**, exactly as specified:

1. **Pour qui** — for me / it's a gift (drives everything after it)
2. **Le coffret** — Duo, Trio, Découverte, Oud, Maison, or Signature (free mix, up to 8 pieces)
3. **Le contenu** — pick the perfumes, diffuseurs and oud weights that fill the slots
4. **Personnalisation** — box colour, ribbon, engraving on the card, message
5. **Livraison** — recipient, phone, address, date, hide prices, send directly (gift mode only)

Price = contents − coffret discount + écrin fee; points = sum of the contents' points (diffuseurs contribute nothing). The whole composition travels with the cart line and into the order.

## Languages — EN · FR · AR

The site ships trilingual with a switcher in the header and footer, and full RTL for Arabic.

- `assets/js/i18n.js` is the engine. **The English page is the key** — no `data-i18n` attributes to maintain. Three passes run over the DOM: whole `innerHTML` of a heading (for copy carrying `<br>` or `<em>`), exact text nodes, then regex rules for strings that carry numbers. A `MutationObserver` re-runs them over anything the pages render later, so JS-built markup is covered too.
- `i18n-content.js` holds catalogue copy (families, ~75 notes, oud specs, coffrets, collections, journal, all 24 product stories). `i18n-labels.js` holds every UI label and sentence, including tab titles (the engine translates `document.title` too).
- **French is the default.** An Arabic browser gets Arabic; English is opt-in through the switcher. Choosing a language stores it under `odys.lang` and reloads. Arabic sets `dir="rtl"`, swaps the UI face to Tajawal, and the stylesheet mirrors the drawer, journey rail, meters, badges and card overlays.
- Composites that mix copy with numbers go through `OD.T()` in the page code, so atoms are translated *before* they are joined.
- Deliberately left in English: brand and product names, prices in MAD and platform names.
- **Search understands French and Arabic.** `QMAP` in `app.js` maps FR/AR query words (sucré, hiver, bâtonnets, حلو, شتاء, مبخرة…) onto the English catalogue vocabulary, handles French elision and peels Arabic prefixes (للشتاء → شتاء). The Discovery prompts are written natively per language.

To add a string: add the English source as a key in the last block of `i18n-labels.js` with its FR and AR values. Nothing else to wire.

## Architecture

- `assets/js/data.js` — catalogue and business config, shaped like a future `GET /api/catalogue`.
- `assets/js/app.js` — one runtime for every page: state, chrome, cart, search, quiz, points, cards.
- `assets/css/odys.css` — token-driven design system; dark sections opt in with `class="dark"`.
- Page code is a `window.PAGE = function (OD) {...}` block in each HTML file, called after boot.

**Cart lines are snapshots** (`{key, id, kind, title, sub, grams, unit, points, qty, meta}`) — a gram weight or a coffret composition survives a catalogue or price edit, and the till never has to re-derive a price.

**State** (cart, wishlist, points, ledger, orders, vouchers, referrals, quiz) lives in `localStorage` under `odys.v2`, read through `S()` and written through `save()`. That is the entire swap surface for a real backend.

**Cache busting.** Every asset URL carries `?v=<stamp>`. After changing any CSS/JS, bump it on all pages:

```bash
sed -i -E 's#\?v=[a-z0-9]+"#?v=NEWSTAMP"#g' *.html
```

**Ratings and reviews are off** (`config.showRatings: false`). The ratings, review counts and the three PDP quotes in the code are demo content; showing invented reviews to real customers is misleading. The product page shows "no reviews yet" with a WhatsApp link instead, the journal's "most reviewed" tab is hidden, and the product structured data carries no rating. Flip the flag only once the numbers are real.

**Structured data.** Every page emits an `Organization` JSON-LD block; product pages add a `Product` with an `Offer` (or an `AggregateOffer` from 5 g to 100 g for oud).

**Oud hints.** Each weight shows "≈ N sticks" from `config.oud.sticksPerGram` (⚠ placeholder: weigh a real stick). Product pages carry a short *Precautions* note per product type.

**Contrast.** `--brass` (#B08D4F) is 2.6:1 on ivory — decorative only. Text and focus rings use `--accent`, which is `--brass-deep` (#7E5F27, 5.0:1) on light and `--brass-lite` on dark. Anything laid *on* `--accent` or `--accent-ink` takes `--ink-on-accent`, which flips with the theme; hard-coding `#fff` or `#1A0B0C` there is how the selected pill ended up ivory-on-sand at 1.4:1.

**Overlays.** The cart drawer and the search bar sit off-screen when closed, so they carry `inert` — otherwise they stay in the tab order invisibly. Opening one makes the rest of the page inert, moves focus inside, and closing returns focus to the button that opened it.

**Product art** is generated SVG — a flacon for parfums, a squat bottle with three rattan sticks for diffuseurs, a bundle of sticks for oud. Replace `OD.bottle()` with `<img>` when real photography exists.

## The product-photo robot

`scripts/studio.js` renders the 3D flacon for every parfum and writes the images the shop and social posts use. The look borrows the layout of tahara.ma's product cards — ivory ground, bottle on one side, name in large serif, three key notes, three words — with our own bottle and our own type.

```bash
npm install                        # once: Playwright, used only by the robot
npm run studio                     # all 12 parfums: shop shot + French card
npm run studio -- odys-02 odys-07  # just these
npm run studio -- --lang fr,ar,en  # cards in several languages
npm run notes                      # ingredient photos from Gemini (needs GEMINI_API_KEY), then studio again
```

It writes to `assets/img/products/`:

| file | size | for |
|---|---|---|
| `odys-02.webp` | 800×1200 | the flacon alone — the shop grid, search, cart and product page (wired through `photo` in `data.js`) |
| `odys-02-card-fr.webp` | 1080×1080 | the square card — Instagram, WhatsApp status, catalogue |

**Every word and colour on the images comes from `data.js`**: name, number, family, gender, the first top / heart / base note, the moods and profile (for the three words), and `juice`, the liquid colour. Change one and run the robot again. Preview any image live at `studio/?id=odys-02&lang=fr` (add `&shot=bottle` for the shop shot).

- **Bottle photographs win over the 3D render.** Save a square photo of a parfum's bottle as `assets/img/bottles/<id>.jpg` (`odys-02.jpg`, or `.png` / `.webp`), bottle centred on a plain ivory background — prompt A in `gemini-prompts.md` makes exactly that — and the next `npm run studio` builds that product's shop image and cards from it. The card takes its background colour from the photo's corners, so the two meet without a seam. ODYS 01 has one; the others fall back to the render until theirs is added. The robot's log says which source each image came from.
- **The flacon** is `assets/js/flacon3d.js`, the same model `bottle3d.html` shows: thick glass, fluted black cap, gold crimp, tinted juice and the white printed label read off the ODYS 01 photograph. A pale juice gets dark ink automatically (below 3:1 contrast, white is unreadable).
- **⚠ Juice colours are guesses** for everything except ODYS 01 (read off the photograph). Set the real ones in `data.js` once the bottles exist — and if a pale juice really is printed in white, say so and the ink rule changes.
- **Note pictures come from Gemini.** `npm run notes` asks Gemini (`gemini-2.5-flash-image`, or `GEMINI_IMAGE_MODEL`) for a studio photograph of each note the cards show — first top, heart and base note of every parfum, about 30 images — and saves them as `assets/img/notes/<note>.webp`. Then `npm run studio` rebuilds the cards with them. It needs `GEMINI_API_KEY` (from Google AI Studio) in the environment; `--all` does every note, `--force` redoes existing ones, and naming notes (`npm run notes -- saffron rose-de-taif`) does just those. A picture that is already there is never replaced, so to get another take of one, delete its file and run again. What each note is photographed as — agarwood chips for *Oud Accord*, sparkling droplets for *Aldehydes* — is the `SUBJECT` table at the top of `scripts/notes-gemini.js`. The card fades each photo's edges into the ivory, so a background a shade off does not show as a square. A note without a picture falls back to a drawn medallion picked by ingredient kind (`studio/notes.js`); a real photograph saved under the same name works just as well.
- Diffuseurs and oud are not drawn yet — the 3D model is the parfum flacon only.

## The flacon in 3D

`bottle3d.html` is a standalone WebGL render of the real 50 ml flacon — drag to turn it, four fixed views, and a button that exports a PNG at three times the screen resolution for use as product artwork. Three.js loads from a CDN at runtime; nothing is installed and no other page depends on it.

The model is built from measurements taken off the supplier photograph (body 1.0 × 1.17 × 0.46, cap 0.458 across and 0.53 tall, walls 0.085), so if the real bottle differs, change those constants at the top of the script and everything follows.

Three things there are deliberate and easy to undo by accident:

- the body is **one merged mesh** (outer shell + inner cavity) drawn with `side: BackSide` — three.js keeps transmissive meshes out of each other's refraction pass, so a separate inner mesh, or `DoubleSide`, turns the glass into a flat grey slab;
- tone mapping is **Neutral**, not ACES — ACES is graded for film and pulls the cream background grey as it passes through the glass;
- the backdrop and floor are **real meshes**, because `scene.background` does not reach the buffer the glass samples.

The model itself lives in `assets/js/flacon3d.js`, shared with the photo robot above. The interactive page is not wired into the shop (the robot's still renders are): putting it on a product page means ~450 KB of Three.js on that page, so it is worth a lazy load and a still image as the fallback.

## Going live

It is a folder of static files: copy it to any host (Netlify, Cloudflare Pages, Vercel, or plain nginx). No build, no environment variables, no database.

1. Confirm everything in the list above, in `data.js` (or test it first in `admin.html`, which only changes your own browser).
2. Put the real WhatsApp number in `config.whatsapp` — with no `+` and no spaces, e.g. `212612345678`. Every order button is a `wa.me` link built from it, so a wrong number means silent lost orders.
3. Set the real domain in `robots.txt` and `scripts/sitemap.js`, then run `node scripts/sitemap.js`.
4. Bump the `?v=` stamp (see Cache busting) so returning visitors get the new CSS/JS.
5. Serve over HTTPS and send these headers (Netlify/Cloudflare Pages read a `_headers` file; nginx uses `add_header`):

```
/*
  Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; script-src 'self' 'unsafe-inline'; frame-ancestors 'none'
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
```

`'unsafe-inline'` is needed because page code and JSON-LD live in `<script>` blocks inside the HTML; drop it if those ever move to files.

**Rolling back** is copying the previous folder over the new one — there is no database to migrate. Keep the last version you shipped.

**Watching it.** There is no analytics and no error reporting, on purpose: any tracker means a cookie banner and a CNDP declaration. The signal is your WhatsApp inbox — if orders stop arriving after a deploy, open the site in a private window and check that the order buttons still open WhatsApp with a filled basket. If page code throws, the page now shows an apology with the WhatsApp button instead of going blank.

## Not built

- **Backend.** No server: no real orders, stock, payments, auth or email. `data.js` + `admin.html` are the contract a backend would fill.
- **Accounts are local** to the browser; checkout records an order object and awards points so the full loop is testable.
- Special orders above 100 g are priced and added to the cart, but the "team confirms the final price" step is a human one — flag those orders in the admin queue when the backend exists.
